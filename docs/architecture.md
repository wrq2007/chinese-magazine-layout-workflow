# 架构：一个编排体 + 两种分工

> 2026-09-20 改版。此前这里是"双运行体"（Codex 编排 + DeepSeek Harness 视觉/文案）。
> 改版原因与实测对照见下面第三节。

```
            ┌───────────────────────────────────────────┐
            │   Codex（编排 + 量测 + 验收）              │
            │   版式引擎 / 脚本量测 / 读图看观感 / 交付   │
            └───────────────┬───────────────────────────┘
                            │
        ┌───────────────────┼───────────────────────┐
        ▼                   ▼                       ▼
  本地多模态模型      冷启动复核子代理            同一台 InDesign
  审美第二意见        零上下文独立复核            （stdio MCP）
  文字审计初筛        （另一条技术路线）
```

## 一、谁做什么，为什么

| 任务 | 归谁 | 理由 |
| --- | --- | --- |
| 量尺寸 / 查重叠 / 验出血 / 验墨色 / 文字保真 | **脚本** | 模型擅长"看"，不擅长"量"，更不适合"认字"；脚本秒级出结论且可复现 |
| 判断"这一页好不好看"、留白与重心是否成立 | **Codex 读图** | 它同时握着脚本、项目规则与交付权，看完能直接改 |
| 审美第二意见（另一套权重） | **本地多模态模型** | 唯一不同模型家族的意见；本地调用零费用 |
| 定稿前的独立复核 | **冷启动子代理** | 零上下文 = 一个不知道我怎么想的审查者；与排版同工作区，能直接读文件 |
| 需求理解、脚本排错、跨文件一致性 | **Codex** | 本地模型实测漏过这类判断（详见 cost-routing.md） |
| 生成多种文案方案 | **Codex** | 生成多样方案是语言模型强项 |

一条贯穿全流程的硬规矩：**模型只负责"看懂画面内容"和"判断观感"；
几何走程序化量测，文字走 PDF 抽字符。** 实测视觉模型会把版面比例 16% 说成 48%，
也会把署名「翟翊翔」读成「曹玥玥」——图片进模型前必被降采样。

## 二、模型接入（本机配置）

| 模型 | 用途 |
| --- | --- |
| `deepseek-flash` | 默认；**文本 + 图像输入** |
| `deepseek-v4-pro` | 复杂推理、长文 |

- 图片输入支持 `image` 模态，可用 `image_detail=original`。
- API Key 只从凭据文件或**环境变量**读取（环境变量优先），**不写进代码与配置的明文**。
  本仓库所有脚本都不含任何密钥。
- ⚠️ 官方接入脚本会强制写 `web_search = "disabled"`，需要联网检索的话记得改回 `"live"`。

> 旧型号 `deepseek-v4-flash-vision-exp` 已下线，不要再引用。

## 三、为什么不再需要第二个运行体（2026-09-20 实测）

原先的假设是"Codex 看不了图，所以找 dsh 当眼睛"。现在 Codex 侧已具备图像输入，
于是做了一次**同一份成品、同一份盲审任务书**的对照（对象：《赞美发现》发刊词定稿）：

| | 外部工具链（DeepSeek Harness） | 冷启动子代理 |
| --- | --- | --- |
| 耗时 | ≈7 分钟 | ≈15 分钟 |
| 覆盖面 | 发刊词 6 条 | 发刊词 4 条 + 通透 7 条 |
| 独家发现 | ① 文字是三色版叠浅色（K=0）② PDF 无输出意图/ICC | ① 图注 K62 对纸白仅 4.07:1 ② 图注折行后剩单个西文词 ③ 9/10 位图超 300% 墨量 |
| 数值准确度 | 背景 TAC 报 190.2%，实测 **297.3%（错）** | 报 297.6%（**对**） |

结论：**覆盖面与准确度互有胜负，没有哪一边明显更强。** 那就换成子代理——
它和排版在同一个工作区、同一套脚本、同一份项目规则，少维护一个工具链与一份凭据，
而且一次能覆盖多件成品。

**顺带更正一个算错的账**：两个运行体走的是同一个 DeepSeek API key，
所以换掉它**并不省额度**，子代理一样按 token 计费。省下的是活动部件与等待。

**比"用谁"更重要的那条**：两边抓到的独家发现都立刻固化成了 `qc-all` 的检查项
（新增文字墨色色版构成、输出意图、图注对比度/残字/间距三项，并给 TAC 加了"贴线"提醒）。
复核者的价值随"它的发现被脚本吸收"而递减——只有变成脚本，下一轮才不必重复同样的劳动。

## 四、InDesign 侧的关键配置（实测）

```yaml
# ~/.dsh/profiles/web/cordis.patch.yml（旧的 dsh 配置，保留作参考）
- insert:                    # ← 必须用 insert 列表形式，直接写 id/config 会报 "patch: entry not found"
    - id: mcp-indesign
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        transport: stdio
        serverName: indesign
        command: node
        args: ['<你的路径>/indesign-mcp-server/index.js']
        env: { INDESIGN_PROGID: InDesign.Application.2026 }
        toolCallTimeoutMs: 120000
        failOnStartupError: true
```

现在走 Codex 侧的同一条 stdio MCP：

```powershell
$env:INDESIGN_PROGID='InDesign.Application.2026'
node work\id-run.mjs <脚本.jsx>
```

- 端口经验：Web UI 用 8090，**不要用 3080**（落在 Windows Hyper-V 保留端口段，绑定时报 EACCES）。
- 技能目录形式：`<技能名>/SKILL.md`（只扫描一层），名称 kebab-case，必须有 `name` 与 `description`。

## 五、并行安全（多个会话共用一个 InDesign 时必须遵守）

1. **只操作自己打的 `label` 文档**——按 label 查找，绝不依赖"当前活动文档"；
2. **把一次任务压成一次调用**（建 → 排 → 导 → 查 → 存 → 关），缩短交错时间窗；
3. **收工恢复原来置前的文档**并关闭自己创建的文档（释放 `.idlk` 锁）。

## 六、性能实测（本机，2026-09）

| 环节 | 耗时 | 说明 |
| --- | --- | --- |
| 直接调用 DeepSeek 文本 API | ~1.3 s | 模型是**推理模型**，会先输出思维链 |
| 直接调用 DeepSeek 视觉 API（5MB base64 大图） | 2–4 s | 视觉本身不慢 |
| `qc-all` 十项验收（4 页稿） | **4–10 s** | 纯脚本，不含模型 |
| 版式引擎渲染一本 7 页样张（含 4 张图） | **5.6 s** | 单次 InDesign 调用完成建→排→导→查 |
| 外部工具链整轮独立复核 | ≈7 分钟 | 主要花在自写量测脚本 |
| 冷启动子代理整轮独立复核 | ≈15 分钟 | 同上；覆盖两件成品 |

**结论**：想快，就别让模型做能交给脚本的事——把"看"和"写"交给模型，把"算"和"验"交给脚本。

## 七、已知坑（与本层相关）

| 坑 | 表现 | 对策 |
| --- | --- | --- |
| 推理模型 `max_tokens` 太小 | 回复**空内容**（思维链把额度吃光） | 给足上限（本地 27B 实测给 6000）；发现"回空"先查这项 |
| 让视觉模型估比例 | 给出错误结论（16% → 48%） | 几何一律程序化量测 |
| 让视觉模型抄字 | 小字读错（「翟翊翔」→「曹玥玥」、「nomadict」→「nomadicst」） | **视觉模型不用于核对文字**；文字一致性只走 PDF 抽字符 |
| 零上下文复核者拿到不全的前提 | 把用户已拍板的事当缺陷重提（例：文首署名按用户要求删除，复核报"缺 13 字"） | 盲审任务书必须写全"已知前提/设计决定" |
| 只抽查部分页面 | 问题恰好出在没查的页 | 逐页验收；报告里写清"验了哪些、没验哪些" |
| 拿复核结论直接采信 | 复核者也会算错（背景 TAC 报 190.2%，实际 297.3%） | **它报的每个数我都自己复算一遍**；复核结论是线索不是权威 |

## 八、这套分工的由来

一开始把"看成品"和"算数据"都交给模型，结果又慢又不准；后来拆成**模型看、脚本量**，
速度提高一个数量级，误判也消失了。再往后发现"自查只覆盖它被写进去的那部分"，
于是加了独立复核；复核每抓到一个新类型，就把它变成脚本里的一个检查项。
这不是理论推导，是这一路上撞出来的（完整清单见 `skills/layout-qc/references/mistakes-log.md`）。

# 架构：双运行体 + 模型分工

这套工作流不是"一个 AI 在干活"，而是**两个运行体共用一个 InDesign**，
分别承担"编排与验收"和"看东西与写文案"。理解这一层，才能理解为什么它能同时做到快和准。

## 一、运行体

```
                ┌─────────────────────────────┐
                │   InDesign（单一实例）        │
                │   COM / ExtendScript 执行     │
                └──────────────┬──────────────┘
                               │ 同一个 MCP 桥接协议（stdio）
          ┌────────────────────┴────────────────────┐
          │                                         │
  ┌───────┴────────┐                       ┌────────┴─────────┐
  │  Codex（编排体） │                       │ DeepSeek Harness  │
  │  本仓库驱动的 agent│                     │ （dsh，视觉/文案体）│
  └───────┬────────┘                       └────────┬─────────┘
          │                                         │
   版式引擎 / 验收脚本 / 配置                     视觉复读 / 文案生成 / 图像理解
          │                                         │
          └────────────► 同一批交付物 ◄─────────────┘
```

两个运行体各自拉起**自己的 MCP 子进程**连接同一台 InDesign，互不干扰的前提是三条纪律（见第四节）。

## 二、模型分工（依托 DeepSeek 的视觉与语言模型）

**dsh = DeepSeek Harness**：一个把 DeepSeek 模型与本地工具（MCP、文件、命令行）接起来的运行框架。
本工作流用它承担**"需要看、需要写"**的部分；用 Codex 承担**"需要精确、需要复核"**的部分。

| 任务 | 谁做 | 为什么 |
| --- | --- | --- |
| 看成品图、逐字转录文字、判断字体形态（衬线/无衬线、字重） | **dsh（DeepSeek 视觉模型）** | 这类"读内容"的任务视觉模型很强，成本低；实测它抓出过"标题其实是宋体""右页下半幅压成平黑" |
| 判断版面比例、量尺寸、查重叠、验出血 | **脚本（Codex 编排）** | 视觉模型对几何量测**不可靠**（实测把 16% 说成 48%） |
| 出海报文案、署名方案、标题变体 | **dsh（DeepSeek 语言模型）** | 生成多样方案是语言模型强项 |
| 图像理解（照片里是什么，决定版式怎么放） | **dsh（视觉模型）** | 先看懂内容再排，比盲排可靠 |
| 驱动 InDesign、跑版式引擎、跑验收、出交付物 | **Codex + 脚本** | 需要确定性、可复现、可量测 |

### 可用的 DeepSeek 模型（本机配置）

| 模型 | 用途 |
| --- | --- |
| `deepseek-flash`（V4.1 Flash） | 默认，文本 + 视觉 |
| `deepseek-v4-flash-vision-exp` | 实验视觉 |
| `deepseek-v4-pro` | 复杂推理/长文 |

API Key 只从凭据文件或**环境变量**读取（环境变量优先），**不写进代码与配置的明文**。
本仓库所有脚本都不含任何密钥。

## 三、dsh 侧的关键配置（实测）

```yaml
# ~/.dsh/profiles/web/cordis.patch.yml（用户补丁层）
- insert:                    # ← 必须用 insert 列表形式，直接写 id/config 会报 "patch: entry not found"
    - id: mcp-indesign
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        transport: stdio
        serverName: indesign
        command: node
        args: ['<你的路径>/indesign-mcp-server/index.js']
        env: { INDESIGN_PROGID: InDesign.Application.2026 }
        toolCallTimeoutMs: 120000
        failOnStartupError: true
```

- 启动 Web UI：`dsh web --port 8090`（**不要用 3080**：落在 Windows Hyper-V 保留端口段，绑定时报 EACCES）
- 校验配置合成：`dsh --profile web --dump-config`
- 一次性任务：`dsh --profile headless "任务文本"`（文本与视觉都支持，视觉直接给图片路径）
- **dsh 自带技能系统**：从 `<项目>/.dsh/skills`、`<项目>/.agents/skills`、`~/.dsh/skills` 读取，
  目录形式为 `<技能名>/SKILL.md`（只扫描一层），名称为 kebab-case，必须有 `name` 与 `description`。
  本仓库的 `skills/` 直接复制到这些目录即可被 dsh 使用。

## 四、并行安全（两个运行体共用一个 InDesign 时必须遵守）

1. **只操作自己打的 `label` 文档**——按 label 查找，绝不依赖"当前活动文档"；
2. **把一次任务压成一次 `execute_indesign_code` 调用**（建 → 排 → 导 → 查 → 存 → 关），
   缩短与另一个运行体交错的时间窗；
3. **收工恢复原来置前的文档**并关闭自己创建的文档（释放 `.idlk` 锁）。

## 五、性能实测（本机，2026-09）

| 环节 | 耗时 | 说明 |
| --- | --- | --- |
| 直接调用 DeepSeek 文本 API | ~1.3 s | 模型是**推理模型**，会先输出思维链 |
| 直接调用 DeepSeek 视觉 API（5MB base64 大图） | 2–4 s | 视觉本身不慢 |
| `dsh --profile headless` 一次性任务 | ~4 s | 其中约 3 s 是**整个插件树冷启动** |
| 同一任务改用 agent 模式多轮工具调用 | 2.5 分钟+ | 慢的不是模型，是"它自己裁图、放大、反复核对"的多轮往返 |
| 版式引擎渲染一本 7 页样张（含 4 张图） | **5.6 s** | 单次 InDesign 调用完成建→排→导→查 |

**结论**：想要快，就别让模型做能交给脚本的事——把"看"和"写"交给模型，把"算"和"验"交给脚本。

## 六、已知坑（与本层相关）

| 坑 | 表现 | 对策 |
| --- | --- | --- |
| 推理模型 `max_tokens` 太小 | 回复**空内容**（思维链把额度吃光） | 给足上限；发现"回空"先查这项 |
| 让视觉模型估比例 | 给出错误结论（16% → 48%） | 几何一律程序化量测 |
| 只抽查部分页面 | 问题恰好出在没查的页 | 逐页验收；报告里写清"验了哪些、没验哪些" |
| 官方 OpenAI 文档不可达（部分网络） | 403 / 超时 | 明确说明"不可引用官方文档"，改用本机实测 + 已核实来源 |

## 七、这套分工的由来

一开始我们把"看成品"和"算数据"都交给模型，结果又慢又不准；
后来拆成**模型看、脚本量**，速度提高一个数量级，误判也消失了。
这不是理论推导，是这一路上撞出来的（完整清单见 `skills/layout-qc/references/mistakes-log.md`）。

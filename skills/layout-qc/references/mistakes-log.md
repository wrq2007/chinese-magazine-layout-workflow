# 错误档案（真实踩过的坑）

这份档案只记录**实际发生过**的错误：现象 → 根因 → 正确做法 → 现在由什么检查兜住。
交付前遇到同类任务，先扫一遍这份表。

## A. 我自己在流程上犯的错（最值得警惕）

### A1. 只验了部分页面就宣称"已验证"

- **现象**：交付时我说"视觉模型复核过了"，实际只验了封面与中间一页；**问题恰好出在没验的第 2、3 页**（标题压正文）。
- **根因**：把"抽查"当成"验收"，而且先下结论再补证据。
- **正确做法**：**逐页**验；验证范围没覆盖的部分，必须明说"未验证"。
- **兜住**：`SKILL.md` 流程第 4 步要求逐页；报告必须写清"验了哪些、没验哪些"。

### A2. 把视觉模型当量具

- **现象**：用视觉模型判断版式比例，它把 16% 说成 48%，据此误判"上满下空、排版失衡"。
- **根因**：视觉模型擅长"读内容"，不擅长"量几何"。
- **正确做法**：**比例、尺寸、对齐、边界一律程序化量**；视觉模型只用来描述元素与判断观感
  （**不用于核对文字**，理由见 B20）。
- **兜住**：`SKILL.md` 核心立场；`measure-export.ps1` 输出毫米坐标。

### A3. 同一个坐标在两个脚本里各算一次

- **现象**：连续两轮出现"标题压正文"：先是标题框 24–40mm 与栏框起点 28mm 重叠；改完又变成副标题 42–52mm 与栏框起点 42mm 重叠。
- **根因**：栏框起点写在骨架脚本、标题位置写在内容脚本，**没有单一来源**；改一处必漏一处。
- **正确做法**：建立**单一来源**的版面常量（本项目：栏框起点 = 页边距 + 30mm = 48mm，且约定"标题区必须整段落在 48mm 之上"）。
- **兜住**：`scripts/check-overlap.jsx` 程序化检查框重叠。

## B. InDesign 自动化错误

### B1. 页面尺寸按磅传，做出 A0

- **现象**：想要 A3，导出成 6629×9374 px（A0）。
- **根因**：`documentPreferences.pageWidth` **跟随文档标尺单位**（默认毫米），传 297×2.8346=841.89 就变成 841.89mm。
- **正确做法**：单位设毫米后写 `pageWidth = 297`。
- **兜住**：`measure-export.ps1` 用「像素 ÷ DPI」反推物理尺寸并判定偏差。

### B2. 单位同时管字号/行距，文字被撑爆

- **现象**：封面文字在成品里"消失"；查 PDF 第 1 页文字操作符为 0 个。
- **根因**：`scriptPreferences.measurementUnit = MILLIMETERS` 时，`pointSize = 33`（本意 33pt）被当作 **33mm**，文字远超框宽 → 全部溢出。
- **正确做法**：脚本统一用**磅**；坐标用 `P(mm) = mm × 2.8346` 换算，字号/行距直接写磅值。
- **兜住**：导出前检查 `textFrame.overflows`（本次已纳入自检）；成品量测。

### B3. 混用单位，对象被丢到粘贴板

- **现象**：脚本报告"每一步都成功"，但页面上只有 1 个文本框，其余 23 个不见了。
- **根因**：单位是毫米，却把「毫米 × 2.8346」当磅传 → 坐标被当毫米解读，对象落到页面外，`parentPage` 为 **null**。
- **正确做法**：一个脚本内只用一种单位并在开头显式设置。
- **兜住**：逐页对象数自检（`P1:r2/t3 P2:r0/t3 …`）；框重叠检查。

### B4. 对页文档里右页的坐标原点在"跨页"

- **现象**：给第 3 页创建的文本框落在第 2 页上。
- **根因**：对页文档中**右页对象的 x 坐标按跨页原点计算**，需要额外加一个页宽；而 `page.bounds[1]` 在不同状态下返回值不可靠。
- **正确做法**：右页偏移用确定性公式（偶数索引(0基)且非首页 → +页宽）；自动化批量生成优先用**非对页**模式，最后再在 InDesign 里开对页。
- **兜住**：对象数自检 + 框重叠检查。

### B5. 母版建了却没应用，页码一个都不出现

- **现象**：母版 `A-正文` 上有页码，页面上却没有。
- **根因**：创建母版 ≠ 应用母版，必须 `page.appliedMaster = master` 逐页设置。
- **正确做法**：建完母版立即逐页应用（首页/封面可单独解除）。
- **兜住**：导出后检查页码是否真实出现在页面上（视觉复核会直接指出"无页码"）。

### B6. 目录页码对不齐（右对齐制表位不生效）

- **现象**：目录五个条目的页码右端参差（411/412/411/399px）。
- **根因**：没设制表位；实测在本机 InDesign 里给故事加 `TabStopAlignment.RIGHT_ALIGN` 制表位**不生效**。
- **正确做法**：页码单独放一个右对齐文本框（与条目框行距一致，逐行对齐），并收窄条目框避免两框重叠。
- **兜住**：视觉复核对目录页量"各页码右端 x"。

### B7. PDF 导出没有出血

- **现象**：PDF 的 TrimBox = MediaBox = 0mm 出血，满版内容裁切会露白边。
- **根因**：默认不导出文档出血设置。
- **正确做法**：`app.pdfExportPreferences.useDocumentBleedWithPDF = true`。
- **兜住**：`references/production.md` 交付清单。

### B8. 图片上的文字用了 Paper 色板 → 看不见

- **现象**：封面/图版上压在照片里的文字完全不显示。
- **根因**：`Paper` 是纸张色（透明性质），叠在图片上不可见。
- **正确做法**：自建 RGB 白色色板（255,255,255）用于图上文字。
- **兜住**：成品量测（亮色文字包围盒）+ 视觉复核。

### B9. JPG 导出忽略 pageString

- **现象**：逐页导出得到 8 个**大小完全相同**的文件，误以为"每页内容一样"。
- **根因**：InDesign 的 JPG 导出只认文件名，**一次导整本**：文件名给第 1 页，其余页在文件名后**追加页码**（`pg.jpg`、`pg2.jpg`…`pg8.jpg`）；`exportResolution` 与 `pageString` 不按预期生效。
- **正确做法**：一次导出整本，按"文件名 + 页码"规律取用；导出后校验各文件哈希/尺寸不同。
- **兜住**：导出脚本按规律命名 + 人工核对文件尺寸。

### B10. 推理模型 max_tokens 太小返回空

- **现象**：API 调用返回空内容。
- **根因**：这些模型先输出思维链，`max_tokens` 被推理耗尽（实测 600 上限时推理占 532）。
- **正确做法**：给足上限；发现"回空"先查这一项。

### B11. 无 BOM 的 UTF-8 脚本被 PowerShell 按 ANSI 解析

- **现象**：自己写的 .ps1 一跑就报语法错误，报错行指向中文注释或字符串，看起来像"代码写错了"。
- **根因**：Windows PowerShell 5.1 读无 BOM 的 UTF-8 文件时按系统 ANSI 代码页解码，中文变乱码，
  引号/括号配对被打乱。**同一坑在本次会话里踩了三次。**
- **正确做法**：脚本里含中文时，保存为 **UTF-8 with BOM**；或用 `pwsh`（PowerShell 7，默认 UTF-8）。
  用脚本生成/改写 .ps1 后，统一补 BOM：
  `[IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding $true))`

### B12. 给 PDF 导出传了预设 → 出血设置被覆盖

- **现象**：明明设了 `useDocumentBleedWithPDF = true`，导出的 PDF 却是 TrimBox = MediaBox = 成品尺寸，**0mm 出血**。
- **根因**：`doc.exportFile(..., using: 预设)` 会用预设里的设置**整体覆盖** `app.pdfExportPreferences`，
  包括"使用文档出血设置"这一项。脚本里先设出血、再传预设，等于白设。
- **正确做法**：要控制出血/色彩就不要传预设，改为显式设置：
  `pp.useDocumentBleedWithPDF = true` + `pp.pdfColorSpace = PDFColorSpace.REPURPOSE_CMYK`（不传第 4 个参数）。
- **验收**：导出后直接读 PDF 的版面盒——`/TrimBox` 应为成品尺寸、`/BleedBox` 应比它大出两个出血值。

### B13. 多任务并行时踩到别人的文档（并行安全）

- **背景**：同一台机的 DeepSeek Harness 会话可能正通过它自己的 MCP 子进程驱动**同一个 InDesign 实例**。
- **风险**：脚本若依赖 `app.activeDocument`，会分析/修改到别的任务正在编辑的文档；
  脚本结束时若不恢复原来置前的文档，也会把对方的界面切走。
- **正确做法**：
  1. 只操作**自己创建的**文档——给文档打 `label`（如 `ForewordBuild`）并按 label 查找，不用 activeDocument 兜底。
  2. 开工前记下当时置前的文档名，收工后恢复。
  3. 恢复要用 `doc.windows[0].bringToFront()`——**Document 对象没有 `bringToFront()`**（踩过）。
  4. 把整套 InDesign 操作压成**一次** `execute_indesign_code` 调用，缩短与他人的交错窗口。

### B14. 排版本身违反了自己写下的规范（最典型的一类）

做一页序言时，我一边在 skill 里写着"行宽 25–35 字""小字别用细字重"，一边交出了：

- 版心 143mm、**每行 38 字**（超出自己定的上限）
- 正文 10.5pt 宋体**反白**压在暗图上（宋体字面小 + 反白变细，双重打折）
- 眉标与署名用 **Light 字重 9.5pt**，压在亮部
- **首行缩进 + 段间空行同时用**（段落层级重复表达）
- 数字用宋体自带的拉丁字形（"60周年""2025.10.18" 全是劣质西文）
- 抒情散文用了"无衬线标题 + 宋体正文"的新闻式组合，**文体与用字不匹配**

**根因**：把"规范"当成写给别人的文档，排版时凭手感做，没有在交付前**拿规范逐条对照自己的成品**。

**正确做法**：排完中文正文后必跑 `scripts/check-cjk-typography.jsx`（避头尾／标点／缩进／中西文字体／行宽）
与 `scripts/check-contrast.ps1`（反白对比度），把规范变成**可执行的检查项**，而不是记忆里的原则。

### B15. 重排格式时把原文的字符改丢了（内容保真的底线）

- **现象**：优化署名格式后，原文的"动**&**静影像工作社"变成了"动静影像工作社"——`&` 被我在改写字符串时漏掉。
- **发现方式**：视觉复核放大到 8× 逐字比对原文 docx，才看出来。
- **根因**：把"重排格式"当成了"重写文本"，没有把原文当作**逐字不可变的输入**。
- **正确做法（按用户要求：靠不变式，不靠事后检查）**：
  1. **文本只复制粘贴**：一律由脚本从源文件读入、原样流入排版，**不手打、不改一个字**；
     确需拆行/拆段时用程序切分，绝不重新键入。
  2. 不增、不删、不改：标点、数字、空格、`&` `·` `—` `…` 这类特殊符号全部照抄。
  3. 需要改内容先问用户。守住这三条，就不需要逐字比对（`scripts/compare-text.py` 已移出例行流程，按需备用）。

### B16. 被自己的检查放过、却被"另一双眼睛"抓住的三件事

同一页序言，我自查通过、视觉复核仍然抓出三条：

1. **反白小字的色温与底不匹配**——冷调照片上用暖金小字，实测显脏；改为同一冷中性色系的明度分档后才成立。
2. **层级档差不足**——12/10/9pt 看上去只有"1 大 + 2 小"两档，视觉实测仅 1.16× 与 1.10×；改成 ≥1.25 倍递增才读得出三级。
3. **内容被我改错**——手打重排时把"动&静"的 `&` 漏了，还把作者写的逗号改成顿号。

**教训**：程序化检查（尺寸／避头尾／对比度）抓得到"规范问题"，抓不到"观感层级是否成立"与"内容是否保真"。
所以交付前必须**两件都做**：跑脚本 + 让另一个视角（视觉模型/他人）逐字与整体各看一遍。

## C. 使用建议

1. 开工前扫一遍 A 类（流程错），收工前跑 `scripts/check-overlap.jsx` 与 `measure-export.ps1`。
2. 出现新的错误，按同样格式追加到本文件——**只写真实发生过的**，不写想象中的风险。

## D. 多页图文稿（《通透》六页）新踩的坑

### B17. 文本框不会互相避让，脚本也不报错

- **现象**：同一页给两段正文各建一个框，都把下边界写成版心下沿；两个框在几何上**大面积重叠**，
  导出后文字叠印。InDesign 不提示、脚本也不报错。
- **根因**：InDesign 的文本框是绝对定位的，"先建框、再灌文"不会自动往下排；
  用固定高度写死版面时，只要字数少于预期，页面就会出现"内容只占上半页 + 框还在往下延伸"的错觉。
- **正确做法**：**先量后放**——
  1. 建框时高度先给一个很大的值，设 `textFramePreferences.autoSizingType = AutoSizingTypeEnum.HEIGHT_ONLY`；
  2. 读 `geometricBounds` 得到真实高度；
  3. 关掉 autosizing（`OFF`），按测得高度重设 `geometricBounds`；
  4. 下一个块接在这个底边之下，逐个往下排。
  这样"逐块定位"在数学上不可能重叠，同时能报出每页内容的真实底端 y。
- **兜住**：`build-*.jsx` 的 `flow()` 封装 + 逐页"内容底端 y"自检 + `check-overlap.jsx`。

### B18. autoSizing 是绕中心缩放的

- **现象**：设了 `autoSizingReferencePoint = TOP_LEFT_POINT`，框仍以**中心**为基准收缩，
  测完高度后拿到的坐标整体位移（实测 700pt 高的框缩到 102pt，框顶从 0 跑到 298.75）。
- **根因**：本机（InDesign 2026）该参照点设置未生效。
- **正确做法**：只用它**测高度**，不要用它的坐标；拿到高度后自己重设 `geometricBounds`。

### B19. 小字截图的分辨率会把版式锁死

- **现象**：教程类稿件的软件界面截图只有 418–450px 宽。要满足 350dpi 备料标准，
  只能放到 **28–30mm**；放到 60mm 就掉到 177dpi。于是"图文对应"的页面必然出现大片留白。
- **正确做法**：拿到素材后**先算每张图在 350dpi / 300dpi 下的最大可用宽度**，再据此决定页面骨架；
  不要先定"图文并排、图占半页"的版式，最后才发现图放不大。留白要在设计阶段就当版式特征处理。
- **兜住**：`check-pdf-print.py` 逐图报有效 DPI。

### B20. 视觉模型会把整页缩略图上的小字读错（最危险的一类）

- **现象**：整页 300dpi JPG 交给视觉模型，它把署名"**翟翊翔**"读成"**曹玥玥**"，
  把图注"nomadict"读成"nomadicst"。若据此回改排版，就会把对的改成错的。
- **根因**：整页图会被下采样到千像素级，13pt 以下的小字在它眼里已经失真。
- **用户定下的规矩（2026-09）**：**最后复核不许用视觉模型核对文字**。图片进模型前必然被压缩，
  小字读数不可信——这不只是"要放大再看"的精度问题，而是"这条路径本身不该用来读字"。
- **正确做法**：
  1. 文字一致性只走一条路：**从 PDF 抽字符**（`page.get_text()`）与源文对照
     → `scripts/check-text-fidelity.py`，给出"字符集是否完全一致 + 标点计数表"的字符级证据。
  2. 视觉模型只保留两个用途：描述"看到了哪些元素"、判断整体观感与结构。
     **问它问题时不要让它抄字**；要问就问"这块留白是不是过大""这张图有没有被压扁""文字有没有被线条压住"。
  3. 关键字符串（人名、社名、`&`、日期、数字）如需目视确认，用 ≥300dpi 的局部放大裁切，
     且结论仍以 PDF 抽文为准。
- **兜住**：`check-text-fidelity.py`（文字）+ `verify-page-crop.py`（观感，明确禁止用来读字）。

### B21. 长文本页会让推理模型把额度全烧在思考上

- **现象**：`max_tokens` 给 4000 返回空；加到 9000 仍返回空——只有文字最多的那一页反复失败。
- **根因**：推理模型的思维链先花掉额度，留给正文的就不够了；**页面文字越多，思考越长**。
- **正确做法**：长文本页**拆成上下两块裁切**分别提问（顺带提高小字清晰度）；
  或把提问压到"只回答 4 项硬伤"，不要让它在一步里既转录又评审。

### B22. `colorBitmapSamplingDPI` 会真的把图降采样

- **现象**：放置 2458px 的原片，导出 PDF 后量到只有 758px（= 350dpi）。
- **说明**：导出时设了 `pp.colorBitmapSamplingDPI = 350`，InDesign 会把高于该值的图重采样到该值。
  这是**预期行为**、也是省体积的正规做法，但交付说明里必须讲清"PDF 内图像是 350dpi 重采样结果"，
  不要写成"原图 2458px 原样嵌入"。

### B23. 视觉模型对"留白"的判断只能当线索，不能当结论

- **现象**：六页里每一页都被判"存在异常大片空白"，但量出来下边距 36–58mm、
  六页内容底线统一落在 205–227mm，是刻意留的呼吸区（本稿内容量本就只够约四页）。
- **正确做法**：先**用毫米量出实际边距与内容底线**，再判断留白是否异常；
  要反驳视觉模型的"留白"判断，用数字，不要用形容词。（呼应 A2）

### B24. `check-layout-rules.ps1` 目前跑不通

- **现象**：`op_Subtraction` on `System.Object[]`，脚本中断。
- **现状**：暂时不可用。页边距类检查改用 PDF 级量测
  （`scripts/check-pdf-print.py`：页面盒 / 出血 / 内嵌字体 / 图像 DPI / 墨迹包围盒反推实际边距）。

### B25. Windows PowerShell 控制台是 GBK，Python 打印字符号会把脚本带崩

- **现象**：`UnicodeEncodeError: 'gbk' codec can't encode character '\u2713'`，
  检查跑到最后一步崩掉，前面的结论白算。
- **正确做法**：Python 脚本开头统一
  `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8', errors='replace')`，
  或干脆用 `[合格] / [不合格]` 这类纯 ASCII 标记。

### B26. 自查里"把某一类元素排除在外"，等于给自己发假合格证

- **现象**：《通透》第 1 页的引文竖线（x 26.0–26.6mm、y 172–202mm）下端伸进正文第二行，
  压住了「手」字的顶部横画。而**我自己的重叠自查报"重叠=无"**——因为代码里写着
  `if (label !== 'rule') { 才检查 }`，把分隔线整个排除在几何检查之外了。
- **抓出它的是**：dsh 的独立复核（它把 PDF 里每个 span 的包围盒与填充矩形求交，
  再放大到 20 倍用眼睛确认），不是我的脚本。**又一次印证：自查只覆盖它被写进去的那部分**。
- **正确做法**：
  1. 几何检查里**不要按元素类型排除**。线、色块、图、文本一视同仁地参与求交；
     确实要放行的（如封面文字压满版图）必须**逐条列白名单并写明理由**。
  2. 加一条专项检查：强调色的线不得进入正文文字区（`check-rule-collision.py`）。
  3. 交付前的独立复核要**换一条技术路线**（这里用 PDF 几何 + 视觉放大），
     而不是把同一个脚本再跑一遍。

### B27. `Pixmap.copy(src, irect)` 的 irect 同时被当作源区域

- **现象**：用 PyMuPDF 拼 6 页联系表，结果**只有第 1 格画出来了**，其余 5 格是纯背景灰。
  文件不报错、能正常打开，只是内容少了一大半。
- **根因**：`Pixmap.copy(source, irect)` 的 `irect` 是"源图与目标图共用"的矩形，
  没有独立的目标偏移参数。第二格起偏移跑到源图外面 → 静默复制了个空。
- **正确做法**：拼版改用 PIL（`Image.new` + `paste(im, (x, y))`），偏移语义明确；
  拼完**回头验一遍每格的暗像素数**，不要只看文件大小/能否打开。
- **抓出它的是**：dsh 复核（它逐个单元格扫像素，发现 5 格是恒定的 245,245,245）。

### B28. 并排两图高度不同时，图注不要强行对齐到同一条基线

- **现象**：高/低对比两张图同宽不同高（88.4mm / 82.5mm），图注却放在同一条基线；
  结果矮的那张图下方多出 6mm 的假空隙，看上去像素"没对齐"。
- **正确做法**：图注**跟着各自的图**（各图底部 + 4mm），基线差一点没关系，
  归属清楚比强行对齐重要。
